# 仓库结构与约定

## 定位

Second Nature 是个人维护、可逐步分享的技能内容库。名称取自英语习语 second nature：熟练到不必刻意思考。仓库旨在把经过验证的工作方法沉淀下来，让它们更稳定地参与 AI 的任务执行。

技能通过任务说明、领域知识、示例和辅助脚本影响行为，不修改模型权重。当前先维护内容、基础工具和评测案例，按实际任务增加技能。

## 指令放在哪里

| 内容 | 更合适的位置 |
| --- | --- |
| 对多数对话都成立的个人偏好 | 客户端个人设置或全局指令 |
| 只适用于某个项目的构建、测试和约定 | 该项目的 `AGENTS.md` 或工具对应配置 |
| 按任务触发、可复用的方法 | 本仓库的 `skills/<name>/SKILL.md` |
| 实际执行确定性操作的程序 | 技能的 `scripts/`，或独立项目 |
| 技能的质量验证输入 | 本仓库 `evals/<name>/` |
| 特定客户端的分发、菜单和依赖封装 | 按需添加的平台适配或 plugin 包 |

`AGENTS.md` 在本仓库中描述如何维护技能，并不代表安装单个技能后会自动加载仓库级规则。因此技能必需的规则要放进它自己的入口或明确引用的资源。

## 目录职责

```text
second-nature/
|-- README.md                    项目介绍与稳定入口
|-- AGENTS.md                    AI 维护此仓库时的约定
|-- LICENSE                      原创内容的默认许可
|-- skills/
|   `-- maintain-docs/           可独立分发的技能包
|       |-- SKILL.md
|       |-- LICENSE
|       `-- references/
|-- evals/
|   |-- README.md                评测方法与工作区约定
|   `-- maintain-docs/           一个技能的完整评测输入
|       |-- cases.yaml
|       |-- fixtures/project/
|       `-- inputs/
|-- templates/                   创建技能与案例的模板
|-- scripts/                     仓库维护工具
|-- tests/                       维护工具的确定性测试
|-- docs/                        随库发布的维护文档
|-- .github/workflows/           持续集成
`-- .local/                     本地笔记、运行结果和临时工作区
```

新增技能沿用 `skills/<skill-name>/` 与 `evals/<skill-name>/`，不增加按工具或领域划分的中间层。名称、用途和触发范围由技能自己的 frontmatter 描述，README 无需逐项登记。

## 哪些内容随库发布

| 位置 | 保存什么 | 是否提交 |
| --- | --- | --- |
| `skills/<name>/` | 入口、许可及执行技能需要的引用资料、脚本和素材 | 是 |
| `evals/<name>/cases.yaml` | 请求、预期行为与输入路径 | 是 |
| `evals/<name>/fixtures/`、`inputs/` | 能复现检查的最小项目、示例文档和输入数据 | 是 |
| `templates/`、`scripts/`、`tests/`、`.github/` | 创建、校验及维护仓库需要的工具 | 是 |
| `docs/`（不含 `docs/research/`）、根 README 与维护约定 | 使用者和维护者需要的长期知识 | 是 |
| `.local/research/` | 调研过程、候选方案、下载的参考材料和个人笔记 | 否 |
| `.local/evals/<name>/` | 评测副本、模型输出、日志、报告和观察记录 | 否 |
| `.local/tmp/` | 临时脚本、草稿、解压内容和一次性检查产物 | 否 |
| 根目录 `tmp/`、`temp/`、`.tmp/`、`research/`、`docs/research/` | 外部工具或单次任务使用的常见临时目录 | 否 |
| 根目录 `outputs/`、`reports/`、`logs/`、`evals/runs/`、`evals/results/`、`*-workspace/` | 工具默认的运行结果、报告、日志及评测工作区 | 否 |
| `.venv/`、Python 缓存、实际 `.env` 文件 | 本机环境、缓存和私有配置 | 否 |

本地目录按需创建，不添加占位文件上库。`.local/` 是本仓库维护工具的首选默认位置，同时保留常见输出目录的根锚定忽略规则，兼容不会自动采用该约定的工具。例如，输出到 `docs/research/` 的研究笔记仍应被忽略，而技能内的 `references/research/` 和 fixture 内的 `tmp/` 可以正常随库保存。

不按 `*.md`、`*.json`、`*.log` 或所有层级的同名目录一刀切忽略，以免丢失技能资源和测试输入。生成内容如果是明确维护的发布制品或样本，仍可随库保存。忽略规则不解除已经存在的 Git 跟踪，新增或调整规则时也要检查索引中的文件。

### 输出路径需要由工具落实

接入新脚本或技能时，先确认它写的是正式交付物还是处理过程中的输出，再检查实际默认路径。临时输出可配置时显式指定到 `.local/`；保留外部工具默认路径时，先确认该路径已被 Git 忽略。无法分类的产物不能仅凭“脚本生成”就自动纳入版本管理。

已有的技能创建器应继续写入 `skills/`，安装操作应继续写入用户指定的客户端位置；两者都是明确的交付动作。校验器只输出终端信息，工具测试使用自动清理的系统临时目录。手工评测按指南复制工作区，优先使用 `.local/evals/`；使用其他本地位置前确认 Git 忽略规则生效。

调研中有用的结论要提炼进相应公开文档，并引用公开来源，不能让仓库功能或说明依赖某个维护者的本地笔记。

## 技能包与评测输入

### 技能独立使用

`skills/<name>/` 只放客户端使用技能需要的内容，必需部分为 `SKILL.md` 和适用的许可通知。`references/`、`scripts/`、`assets/` 及客户端元数据按实际需要添加，并从入口说明读取时机。

使用技能内的相对路径，不依赖根目录的维护工具、评测材料或 `.local/`。保持一份正文，通过显式安装或平台包装适配客户端，不为每个工具复制一份技能内容。创建器会为原创技能复制根 `LICENSE`，支持单独分发。

### 评测输入可复现

每个技能的案例与资源放在同一个 `evals/<name>/` 下。`cases.yaml` 使用仓库根目录相对路径，方便统一解析。fixture 和输入中可以故意保留错误，用来验证技能是否识别问题，不属于日常文档准确性和链接检查的目标。

原始评测输入保持不变。每个案例、对照组和重复运行，都先复制到独立的本地工作区，再执行被测任务。首选位置是 `.local/evals/<name>/`；其他位置必须满足相同的 Git 忽略条件。评测不会直接改动本仓库或版本化 fixture。具体准备与记录方法见 [评测指南](../evals/README.md)。

`tests/` 验证创建器和校验器等维护程序的确定性行为；`evals/` 用真实请求观察 AI 行为。两者各自维护，不把格式通过或单元测试成功当作技能效果的证明。

## 公开文档与本地资料

[仓库首页](../README.md) 讲清项目动机、技能概念、长期原则和阅读路径，通过示意结构帮助第一次访问的读者理解内容。它不维护技能清单、数量、阶段状态、依赖版本或具体操作命令。新增技能和工具适配时，更新对应内容与指南即可；项目定位、长期原则或导航入口变化时再相应修改 README。

环境准备与编写方法放 [编写指南](authoring.md)，安装和客户端差异放 [使用指南](usage.md)，评测准备与执行放 [评测指南](../evals/README.md)。`SKILL.md` 只包含模型完成该任务需要的指导。

随库 Markdown 的链接与图片引用必须指向随库存在的内容或公开 URL，不能指向被忽略的本地文件、仓库外的个人路径或尚未生成的本地产物。文档可以用代码路径说明 `.local/` 的用途，但不能把其中的文件作为读者必需的参考资料。

不强制每个目录或技能都加 README、changelog 或索引，避免重复维护。模板采用 `SKILL.md.template`，放在技能发现目录外；评测源材料与输出也不混入技能发布包。

## 校验与持续集成

默认执行 `python scripts/validate.py`，检查技能基础格式、随库 Markdown 的本地链接发布边界，以及案例定义和输入路径。通过 Git 候选文件集合识别可提交内容，避免“本机存在，但提交后缺失”的链接也通过检查。

维护校验程序时运行 `python -m unittest discover -s tests`。CI 执行这些静态检查和工具测试，不运行模型评测或 fixture 中的程序。单技能格式检查仍可使用 `python scripts/validate.py --path skills/<name>`。

静态检查不验证外部 URL 可用性、页面渲染与锚点、全部客户端专用字段或模型任务质量。格式与路径检查、实际工具执行、模型行为评测分别记录结果。

## 暂缓的建设

用 Git 管理修改记录，直接浏览 `skills/` 查找技能。marketplace、网站、自动发布、全量同步安装器、数据库和独立技能版本体系，按实际需求再引入。

以下需求实际出现后再扩展：

| 实际需求 | 后续建设 |
| --- | --- |
| 多个技能持续复用同一套代码 | 提取稳定的公共程序，并明确安装依赖 |
| 团队需要一键安装和固定版本 | 增加有版本记录的分发方式 |
| 需要 Codex plugin 的其他能力或市场安装 | 增加客户端 manifest 和打包流程 |
| 技能增多后直接浏览难以检索 | 从 frontmatter 生成可分类、检索的目录 |
| 手工评测已形成稳定案例且耗时明显 | 为现有案例增加自动运行与结果采集 |
