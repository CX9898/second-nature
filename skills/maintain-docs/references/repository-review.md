# 仓库级文档检查

用于全仓或跨文档检查。已有明确文件范围时按该范围工作，不必建立新的全局文档体系。

## 盘点与事实来源

先识别项目指令、入口、用户指南、配置/API 参考、架构、ADR、版本历史、示例、模板和生成物。查看文件清单与引用关系，再决定需要深入的区域。

区分自主维护、第三方、历史、内部、研究、生成和缓存内容。遵守各自维护方式，不把 vendor、构建目录和归档中的所有 Markdown 都视作需要统一改写的正式文档。

对需要修改的重要主题记录：文档职责、读者、目标版本、权威事实位置，以及哪些入口或模板引用它。该记录可以在工作过程中保持简短，无需给用户生成一份逐文件流水账。

## 按影响处理

优先处理会使读者执行失败或误判能力的问题：错误命令、目录和路径，缺失前提，错误默认值或优先级，未实现能力、过期兼容条件，以及将可选项写成必需项。

再检查内容归属、重复和导航：完整说明是否有权威来源，入口能否到达，稳定事实是否被多处手工复制，局部修改是否留下冲突描述。最后统一语言、术语和格式。

文档与源码不一致时，先确定目标版本及证据。无法确认哪一方有误的事实作为待确认问题报告；文档任务不自动授权修改产品代码来迎合描述。

## 同步、移动与删除

- 先修改生成源或权威说明，再处理用户范围内的生成结果和引用。已有安全、轻量的生成命令可以使用；不要为同步 README 触发无关的镜像、原生库或产品重建。
- 合并前迁移有效内容。保留理解限制所需的条件、技术细节、公式、示例和图源；篇幅长本身不是删除理由。
- 移动或删除前搜索入站引用，包括文档、模板、脚本、图片和站点配置。修复相关引用，不为消除一条链接直接删除被引用的知识。
- 正式历史、ADR、第三方来源和许可证按其语境维护。存在过时信息并不等于整个文件可以删除。
- 无关的未提交变更保持原状；不要顺带更新忽略规则、安装目录或仓库治理文件。

## 公开与内部语境

公开文档中的秘密和无必要的内部背景需要去除或改成占位内容；检查个人工作目录、内网地址、私有制品位置和未脱敏日志时，结合其用途判断。

内部运行手册可能需要实际部署路径、服务地址和操作角色。保留完成任务所需信息，同时避免暴露凭据。已公开的联系人邮箱、作者身份、许可证及第三方归属不应因简单的模式匹配被删除。

## 检查的证据强度

| 检查 | 能证明什么 | 不能据此声称什么 |
| --- | --- | --- |
| 阅读实现、配置和文档 | 指定内容在目标版本中的一致性 | 所有示例已实测 |
| 链接、语法和格式检查 | 检查范围内的结构与语法有效 | 远端服务可用、依赖兼容或业务正确 |
| 有限命令与小输入测试 | 给定环境和输入下的可观察结果 | 全部硬件、真实数据质量或长期稳定性 |

优先复用项目检查工具和结构化解析器。新增文档检查脚本只有在重复工作或可靠性收益明确时才需要；不要以关键词出现与否代替语义审查。

片段、占位符、模板变量和完整程序采用不同校验方式。检查仓库内链接的目标和锚点，区分导航目录、生成站点路径、版本链接与外部链接；缺少网络或渲染环境时说明限制。

只执行授权范围内的验证。安装、下载、运行大模型、修改服务和清理容器等示例应先按任务权限及副作用判断，不能因为出现在文档中就照做。

## 交付结果

审查结果按影响排序，指出位置、核对依据、读者后果与建议；区分已证实错误、需确认事实和风格建议。只有用户要求修改时才编辑。

修改结果说明关键行为或信息怎样变得准确、哪些文件关系已同步、做了哪些验证及仍有什么限制。全仓检查应交代实际覆盖的区域和排除项；不要把未查看的历史、第三方或生成目录笼统称作已通过。
