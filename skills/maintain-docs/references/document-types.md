# 文档类型与改写判断

先选与目标文档有关的部分。下列内容是检查维度，不是每份文档必须补齐的章节模板。

## 职责与读者

| 类型 | 负责回答的问题 | 控制边界 |
| --- | --- | --- |
| 根 README | 项目是什么、适合谁、主要能力与入口在哪里 | 按项目约定保留最短使用路径，不堆放完整配置、逐文件清单和开发进度 |
| 用户指南与示例 | 有什么前提、如何运行、结果在哪里、怎样判断成功 | 必需条件提前说明，复杂步骤形成连续流程；简单例子无需重复七段说明 |
| 配置与 API 参考 | 字段或参数怎样影响行为 | 核对类型、默认值、优先级、加载时机、状态约束、错误及返回格式 |
| 构建与发布指南 | 维护者怎样构建、验证、生成和更新制品 | 保留必要的工具链和制品关系，区分内部构建与最终用户安装 |
| 架构 | 当前模块怎样协作、数据与制品怎样流动 | 描述已实现结构、接口、配置来源和有实际影响的约束 |
| ADR | 某项决策为什么成立、考虑过什么取舍 | 保留状态、时间、背景、决策和影响；新变化按项目约定修订或增加记录 |
| 算法与技术推导 | 计算如何定义、实现如何对应、误差怎样产生 | 保留符号、布局、公式、舍入与边界、实现对应和验证条件 |
| 目录 README | 这个目录放什么、稳定入口是什么 | 面向实际读者说明当前层级，不展开无关的解压后结构或描述 README 自身 |
| CHANGELOG | 某版本改变了什么、对使用和升级有什么影响 | 选择重要变化，区分产品与独立组件版本，保留正式历史 |
| 贡献指南 | 如何开发、测试、提交与维护 | 采用仓库真实入口和必要要求，不创造团队制度或审批角色 |

一篇文档可以服务多个相关任务，但主要读者和主线应明确。段落混合操作、接口契约、实现解释或迁移历史时，按读者用途调整层次、位置或引用；保留技术知识不要求保留原来的段落排列。

## 判断局部信息价值

以当前章节、段落、步骤或配置项为判断对象，先确定读者此刻要理解的问题、作出的选择或观察的结果，以及从前文和文档用途可以预设的知识。首次使用某项功能不等于缺少专业知识；熟悉领域也不等于掌握产品全部模块和阶段。算法、架构和 ADR 中的概念解释、推导和决策依据本身就是阅读任务。

把整篇目标落实到当前位置的职责，简要形成具体的读者问题；不能把字段或段落的任务扩大成“了解整个系统”来容纳所有相关背景：

| 说明位置 | 当前读者问题的依据 |
| --- | --- |
| 字段、参数与配置块 | 如何填写、何时生效、改变什么行为，及作出该选择所需的机制或风险 |
| 操作步骤 | 当前是否需要执行、何时执行、如何操作、怎样判断结果 |
| 约束或状态说明 | 在什么条件下限制成立，改变状态需要什么，其前后关系如何连续 |
| 概念、架构、算法或决策章节 | 当前概念或问题怎样解释，所需推导、关联与证据是否充分 |

这个问题应来自标题、字段和相邻正文，不能只用“读者有专业基础”或“都属于同一流程”替代。专业读者能读懂附带内容，也仍需判断他是否有必要在这里阅读。

对引入其他概念、重复前文或打断主线的内容，判断它具体增加了什么：如果删除或移位，读者会失去哪项理解、操作条件、风险判断或原理依据？仅能说明它与整个系统相关，还不足以证明应放在这里。若它使读者额外追查概念，却没有帮助回答当前问题，应作为调整候选；必要提醒和独立使用场景中的少量重复仍可保留。

| 判断依据 | 处理方向 |
| --- | --- |
| 当前任务需要，且读者有足够前提 | 保留，保持对象和条件明确 |
| 当前任务需要，但依赖尚未交代的概念或关系 | 就地补最少的关系与影响，详细内容按需引用 |
| 有独立知识价值，但服务另一任务或打断当前说明 | 在授权范围内迁移到合适位置，或引用已有权威说明；不为保存每句话新建章节 |
| 对当前任务没有增量，也无需要保留的独立文档价值；或有效信息已在合适位置覆盖 | 删除冗余，不必逐句另找归宿 |

这些是取舍依据，不是每段必须填的表格，也不规定技术词、跨阶段说明或否定句必须删。需查源码确认的行为与从阅读上下文即可确认的信息负担分别核实。对有争议的候选，保留具体位置和取舍理由，避免在汇总时仅因事实正确而过滤掉。

## 成稿语义检查

按本次任务范围和适用文档类型复核成稿或审查对象。以下是判断问题，不是固定章节、禁用词清单或每段必须套用的模板：

- 读者能否理解当前行为、条件和限制，无需知道作者的对话或修复经过？比较和迁移说明是否明确参照对象、适用版本或状态？
- 按局部信息价值判断，附带概念、相邻重复和话题切换是否服务当前任务？必要的跨模块关联是否交代了关系和影响，而非仅列出术语或链接？
- 默认值、自动行为、必需条件和可选设置是否有明确的对象与生效阶段，能否据此选择实际操作？
- 使用步骤的前提、执行目录、输入输出是否衔接？结果和成功条件能否被读者观察，验证结论是否与证据范围一致？
- 标题是否反映正文职责？主题层次、术语和指代是否一致，技术细节是否位于需要它的读者能找到的位置？
- 对应类型的关键信息是否仍有遗漏或相互冲突，有效约束、推导、示例和来源是否得到保留？

发现其他范围内的问题时继续处理，不能因先前发现已修复而停止。明确标注的历史比较、必要否定和技术细节可以保留；是否改写取决于语境和读者需要。

### 采用与判断相匹配的依据

| 判断 | 依据 | 不能替代它的结果 |
| --- | --- | --- |
| 事实是否准确 | 指定版本的实现、配置、契约或可观察行为 | 文句流畅、例子语法有效 |
| 语义是否清楚 | 读者能从正文及明确引用中辨明对象、适用条件、比较参照和所需动作 | 没有发现与源码矛盾的语句 |
| 结构是否适用 | 标题与正文职责对应，读者能沿主线找到完成任务所需信息 | 文件已分目录、每段技术内容分别成立 |
| 步骤是否可完成 | 所声明环境和初始状态下，前提、命令、对象状态和结果连续衔接 | 单条命令能解析、某个已有环境曾运行成功 |

这些依据用于作出判断，无需复制为交付表格。指出具体位置及对目标读者的影响；不必要的知识前提、关联不明和主题中断，即使命令仍可执行，也可能需要改写。区分这些问题与不影响理解、判断或操作的个人措辞偏好。

复核时以文档声明的读者背景和环境为前提，沿阅读路径已提供或明确引用的信息走完任务；不要用编辑者额外掌握的源码细节、修改经过和已修清单替读者补足未说明的条件。沿途保留执行目录、变量、已有文件和对象状态。按文档声明支持且影响操作选择的路径检查，不要求穷举所有组合。

### 验收表达判断

对审查中形成的理解疑点、重复模式和归属争议，核对最终处理或不报告的理由：是否对应具体原文与读者任务，是否解决额外知识前提、歧义或主题中断，以及哪些必要条件、推导或风险因此保留。仅审查时将成立的问题写入发现；改写时再核对成稿是否落实，避免只给“可以简化”的笼统建议。

无问题结论也应能说明所采用的读者背景，以及所核对的局部说明为何足够或必要；依据要对应同一位置的读者问题和引入的内容，其他章节写得清楚不能替代该处判断。可简要引用有代表性的边界和保留依据，不要求为每句无问题的文字提交记录。宏观阅读顺序清楚、各句技术上正确，不能单独支持局部信息取舍合格。若仍有未判断的区域或争议，限定结论范围，不以覆盖自述代替判断。

### 核对相邻环节的契约

对贯穿多个步骤的数据、对象或制品，确认上游实际产出能否满足下游要求。按相关性检查对象身份、类型、计数单位与数量、就绪状态、参数适用阶段及产物用途；不能只确认各接口描述分别正确。同一名称可能表示不同阶段的对象，同一对象也可能有不同别名，应核对含义而非仅匹配名称。

重点检查本次新增或改变的组合、文档声称可以同时启用的选项，以及会影响操作的默认分支。用一个小而有效的输入贯通相关环节，或沿实际调用链核对输入输出的对应关系；不要求穷举所有组合或运行完整系统。涉及通用公式和特殊处理时，核对其适用范围、处理顺序与例外，不能凭公式本身正确推断所有调用都适用。

对图、表或操作摘要，逐项核对消费方实际读取的对象和所需状态。报告、校验和恢复的用途可能不同，不能因文件格式相同或内容相关就互相替代。组合不受支持时，在文档中限定条件或给出已实现的替代路径，不擅自修改产品代码使说明成立。

## 使用说明与可运行例子

依据读者的任务补足环境、执行目录、输入、命令、输出和成功条件。前提已由上文说明时可以引用，不必在每个代码块重新列出。

- 命令顺序中的目录、变量与输出应能衔接。区分示例占位路径、用户可配置路径和工具固定生成路径。
- 默认流程先说明真实默认行为；可选模式给出启用条件。不要让用户手工决定已由工具自动匹配的内容。
- 涉及模型、数据或实验质量时，区分接口冒烟输入和代表性正式数据。一次随机输入成功不证明生产精度或长期稳定性。
- 资源、硬件和兼容要求按实际支持范围说明，避免把某次测试机器写成唯一使用条件。
- 制品说明依据产物及其消费方：谁需要哪个文件、辅助文件是否可选、怎样加载或使用。不要假定所有发布都必须有 manifest、聚合校验清单或额外元数据。

核对前提时，沿示例实际进入的调用、导入和资源加载路径检查必要依赖，区分完整环境已提供的条件与独立运行需要准备的条件。较长依赖集合可引用权威环境定义，不凭直接入口猜测完整清单。静态走读和小输入验证应与实际执行区分，不为补足证据擅自安装或重建环境。

## 配置参考

追踪配置从创建、加载、覆盖到执行的路径。任务涉及的配置注释和人读的字段说明也按文档审查，以当前字段或配置块的职责判断信息价值；已有字段名足以表达的内容不必换句话重复。必要的开关方向、单位、默认行为、风险和状态约束应保留；跨阶段流程在相应章节或指南展开，字段旁说明理解或使用当前配置所需的关联与影响。

按读者需要选择说明哪些默认行为，不因事实核对涉及某个选项，就在各处介绍未暴露或与当前任务无关的配置维度。需要时将下列值分别说明：

| 值的类别 | 核对位置 |
| --- | --- |
| 新实例的初始值 | 构造函数或数据类定义 |
| 配置缺省字段的加载值 | 解析器、合并器和 schema |
| 示例显式值 | 示例配置及其调用位置 |

还要核对匹配优先级、何时生效、未知字段和非法状态的处理，以及保存、重载、重新校准等操作的必要条件。只写当前接口实际存在的字段，不凭规范补出产品能力。

新增或改写“必须”“先做”“无需”等操作断言时，检查其适用对象、初始状态、触发条件与保证结果，并核对是否存在其他合法路径。某分支会调用一步操作，不足以证明所有使用方式都需要它；状态不同的行为应分别说明，有效替代方式不得被新写的前提排除。

## 发布说明

先判断变化是否值得用户关注，再决定放入新增、变化、修复或升级说明等现有栏目。无需为每个版本增加空栏目。

- 修复说明以触发条件和用户可见结果为主。实现细节只有影响部署、使用或升级判断时才进入正文。
- 升级说明明确需要采取的操作、适用版本与兼容边界。不要在每次发布模板中重复已经结束的历史迁移事件。
- 不把重新构建、重新导出、重新安装或重建运行环境混写成同一件事，实际需要哪一步就说明哪一步。
- 更新指定版本时遵守用户给出的归档范围，不顺带提升其他组件版本或重写既有正式发布历史。

## 架构、ADR 与推导

架构文档与目标版本的模块、接口和数据流对应；图中名称、张量布局、位宽或中间产物与实现一致。沿用已有可维护图源，不为统一风格强制重画全部图。

ADR 的历史决策可以解释过去的约束。按新行为维护当前指南，并以修订、替代关系或新 ADR 说明决策变化；不要让历史记录看起来一直采用新方案。提案和未来工作需要明确实现状态，不能改写为已支持能力。

技术推导按其知识价值维护。通过术语定义、导航、引用和结构改善可读性；保留有效公式、适用条件、误差和实现关系，不以“用户视角”将其压缩成宣传摘要。

## 改写示例

### 同一技术事实在不同位置的用途

假设某工具只接受相同格式版本的检查点，输出文件名不决定格式：

| 阅读位置与任务 | 取舍及依据 |
| --- | --- |
| `output_name` 字段旁，用户正在填写文件名 | 说明命名规则。恢复器如何校验版本不影响此处填写，相关机制放到格式或恢复说明 |
| 恢复步骤，用户正在选择可加载的检查点 | 保留相同格式版本的条件；省略会让用户选择不兼容输入 |
| 格式参考，维护者正在理解解码约束 | 保留版本字段、校验顺序及拒绝不兼容格式的依据；这些技术知识就是当前主题 |

判断差异来自阅读任务和位置，不来自“版本”“校验”“恢复”等术语本身。字段旁移走机制解释，不等于删除恢复条件或压缩技术参考。

### 从实现动作改为用户影响

过程描述：

> 为任意数值 UID 设置默认用户名和临时 HOME，补齐容器初始化变量。

用户可感知的修复：

> 修复以非 root 用户运行容器时，部分模型处理流程因用户名查询失败而中断的问题。

只有读者需要配置这些变量时，才在部署参考中保留变量名和覆盖方式。

### 从对话补充改为目录事实

过程描述：

> 根据之前的要求，本次删除了重复索引，并补充 JSON，方便后面继续核对环境。

目录文件说明：

> 同名 JSON 记录环境组件版本和依赖清单，供查询和问题排查使用。

这一变化是否进入 CHANGELOG，仍取决于它的用户影响；表达合适不代表必须公告。

### 简洁与准确的边界

保留“CPU 不支持 QAT”等真实限制。可以同时给出支持的替代路径，但不要通过删除否定句、弱化精度条件或删掉推导来制造“更好读”的假象。
